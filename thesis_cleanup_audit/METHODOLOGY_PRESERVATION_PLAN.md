# Methodology preservation plan

Read-only recommendation. Nothing has been changed. This synthesizes `CHECKPOINT_SELECTION_PATCH.md` and `PERSISTBENCH_MODIFICATIONS.md` into one concrete plan for how to preserve both pieces of thesis methodology cleanly, before any file migration begins.

## Recommended approach, per modification

The four options in the task (A: wrappers over untouched upstream, B: explicit patch files, C: clean thesis-specific modules, D: small documented modification retained in upstream files) are not mutually exclusive — the right answer differs per modification because the two cases are structurally different: the trainer patch is **thesis-authored logic with no upstream equivalent** (a new checkpoint-selection policy), while most of the PersistBench patches are **environment/routing plumbing** to make an existing upstream code path point at a different server.

## Why not just "keep upstream untouched, wrap everything" (pure option A) for all of it?

Pure wrapping is not achievable for either case without deeper surgery than the task authorizes right now:

- The trainer patch must execute *inside* `Trainer.evaluate()`'s control flow, before HF's own `load_best_model_at_end` logic runs — there's no external wrapper point for that without either monkey-patching (worse, not better, for a grader to follow) or replacing HF Trainer's checkpoint-saving loop entirely (far more invasive than the current 147-line patch).
- The PersistBench judge rewrite must produce a `JudgeResult` at the exact point `evaluate_with_judge` expects one — an external wrapper around the whole benchmark run could substitute a different judge implementation only if PersistBench had a judge-provider plugin interface, which upstream does not currently expose (it dispatches on a hardcoded `if provider == "openrouter": ... elif provider == "vertexai": ...` inside `judgment.py` itself).

So for both cases, **some modification to the vendored/upstream file is unavoidable** if the thesis wants to keep using HF Trainer's and PersistBench's own execution loops rather than reimplementing them. The realistic goal is not "zero modification" but "small, named, documented modification whose logic lives somewhere legible" — which is what the per-row recommendations above describe.

## What must remain in place for existing scripts to work right now (do not touch until migration is executed deliberately)

- `src/trainer/base.py` exactly as it is today — every `*_savebest`/`bestagg_*` checkpoint directory under `saves/unlearn/` and every entry in `supervisor_update/code_settings/trainer_states/` depends on `best_agg` (and, for the earlier TOFU work, `Agg_proxy`/`Selection_proxy`) being computed exactly as currently implemented. If this file's *numeric* behavior changed even slightly (not just its location), re-running any of the four `best_agg`-using launchers could select a different checkpoint than checkpoint-459/checkpoint-51/etc., invalidating the already-selected canonical checkpoints.
- `external/PersistBench/src/benchmark/execution/judgment.py`'s current rewrite — every existing MUSE-News/MUSE-Books judged JSON file was produced by this exact code path; if it's later replaced with a cleaner module, the *existing* output files remain valid (they're already on disk), but any **re-judging** must go through equivalent logic to stay comparable.
- `external/PersistBench/src/benchmark/config.py`'s `JUDGE_MODEL_OPENROUTER = "local-judge"` and `providers/openrouter.py`'s URL/key fallback — needed if any judge run is repeated.
- `external/PersistBench/src/benchmark/utils.py`'s current `STRICT_GENERATION_CONTROL` block — needed if any generation run is repeated *today*, but note (§4c of `PERSISTBENCH_MODIFICATIONS.md`) that repeating a generation run today with this block active will **not** reproduce the exact original 2026-07-08/10/12 generations, because that block didn't exist yet when those ran. This is worth stating explicitly in the thesis's reproducibility section: exact bit-for-bit regeneration of the original PersistBench MUSE-News/MUSE-Books responses is not possible even with today's code, only with code as it stood on the generation date. The existing generation JSON files themselves remain the authoritative record.

None of this should be touched by the file-moving phase of cleanup. `src/trainer/base.py`, `configs/eval/tofu.yaml`, and everything under `external/PersistBench/` are already marked **KEEP IN PLACE** in `MIGRATION_PLAN.md` for exactly this reason — this document doesn't change that, it just explains *why* in enough depth to defend it to a grader, and adds the specific recommendation to extract logic into named modules (`checkpoint_selection.py`, `local_judge.py`) as a **before-migration, deliberate, separately-reviewed step**, not a side effect of moving files around.

## Recommended sequencing (this document only recommends; it performs none of these steps)

1. Write `thesis/docs/trainer_patch.md` and `thesis/docs/persistbench_patch.md` (already scaffolded as empty targets in `PROPOSED_STRUCTURE.md`) using `CHECKPOINT_SELECTION_PATCH.md` and `PERSISTBENCH_MODIFICATIONS.md` as source material — pure documentation, zero code risk, do this first.
2. Verify the `repetition_penalty` provenance discrepancy (§4c of `PERSISTBENCH_MODIFICATIONS.md`) directly with whoever wrote `muse_books_weekly_update_analysis/README.md` (possibly the thesis author's own past self) before the thesis text repeats that specific number.
3. Only then, as a deliberate and separately-tested step: extract `checkpoint_selection.py` out of `base.py`, and (if desired) `local_judge.py` out of `judgment.py` — each as its own small, reviewable change with a before/after test (e.g. confirm re-evaluating one existing checkpoint still reports the same `best_agg` value after the refactor).
4. Only after that, remove the two confirmed-dead code blocks in `utils.py` (§4a) — lowest risk of all the code changes recommended here, since they are proven unreachable, but still worth doing as its own tiny, verifiable commit rather than bundled into a bigger change.
5. Only after 1–4 are done and reviewed does the broader file-migration in `MIGRATION_PLAN.md` proceed, so that the migration is moving already-documented, already-clean code rather than moving mystery patches.

## Answer to "does anything prevent proceeding with cleanup?"

No — as with the MUSE-News track resolution, nothing here blocks the previously planned file migration. What this analysis adds is that **documenting the two patches (step 1 above) should happen before, not after, the migration**, since `MIGRATION_PLAN.md` already defers touching `src/trainer/base.py` and `external/PersistBench/` — so writing the two doc files is pure upside with no dependency ordering conflict with the rest of the plan.
